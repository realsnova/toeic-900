## 0. 摘要

- **目標**：九個面向的加權總分 **≥ 7.5**。商業門檻是 7，多留的 0.5 是評分誤差的緩衝。和前兩次評分一樣，只計算已經上線、可以驗證的功能。
- **為什麼要另寫一份計畫**：原規格刻意限制了範圍：聽力維持 3 分、商業化基礎上限 5 分、不做分數預測。照原規格全部做完（連同 v1.8 的聽力大綱），加權總分最高只有 **6.9**，到不了 7。要超過 7，需要兩件事：
  1. 把聽力列入商業級範圍。聽力佔 10%。
  2. 我們本來就有優勢的四個面向（體驗、工程、安全、學習引擎）要做到 8 分，補回不做付費所少的分數。
- **時程**：分 5 個階段，從 2026-10-10 到 2027-05-31，約 7.5 個月。
- **考前階段 P0**（10/10–10/25）只做對 10/31 考試也有直接幫助的事：
  - 所有聽力題改用預先產生的神經語音音檔；
  - 第 1 回完整聽力測驗。
  
  目標 10/20 上線，10/26–10/31 照原規定凍結。
- **真正的瓶頸不是程式**，而是下面三件事。§3 對每一件都有具體做法：
  1. 約 2,200 道新題和 1,400 個新單字；
  2. 約 8 小時的聽力音檔；
  3. 真實使用者的作答資料。

## 3. 設計

### 3.1 內容資料模型與載入（P1）

**題目格式 v2**：每道題都是一個物件，欄位如下。

| 欄位 | 說明 |
|---|---|
| `id` | 穩定字串，例如 `p5-0412`、`r3-p7-05-2`；發布後不改、不重用 |
| `part` | 所屬 Part |
| `skills[]` | 技能標籤 |
| `lvl` | 編輯估計的難度，1–5 |
| `src` | 批次 ID |
| `rights` | 權利狀態，例如 `original`、`tts:kokoro`、`photo:pexels:<url>` |
| `ev` | 答案證據 |
| `why[]` | 每個選項的對錯原因 |
| `exp` | 繁中詳解 |
| `retired` | 下架標記 |
| `legacy` | 舊陣列索引，只用於轉換 |

- **ID 轉換**：v1.6 開機時執行一次 `migrateToIds()`，把錯題本、完成紀錄、模考紀錄、SRS 的索引鍵換成 ID。
  - 轉換前先自動建立一份本機備份；轉換可以重複執行，結果相同。
  - 舊備份檔照樣可以匯入（INV-03）。
  - 轉換完成後就不再需要 `baseN` 與 `shiftForBuiltinGrowth`。
- **內容分包**：題目從 `js/data/*.js` 搬到 `content/<pack>.json`，依 Part 和批次分包；`content/manifest.json` 記錄每包的題數和雜湊。
  - 開機只載入當日需要的包；Service Worker 會快取。
  - 目標是 3,000 題加 2,000 單字時，首次載入仍 ≤300 KB。現在是全部打包，冷啟動約 290 KB。

### 3.2 內容工廠（P2 開始量產）

沿用並擴充 D-A11 的流程，每批 50–100 題：

1. **批次規格**：指定 Part、技能、難度比例、新制題型比例。
2. **撰寫**：Claude Code 的作者代理直接寫成 v2 格式。不呼叫付費 API，用的是你現有的 Claude Code 額度。
3. **自動檢查**（`tools/lint`），包括：
   - 格式；
   - 重複與近似重複；
   - 正解位置分布；
   - 選項長度偏差，例如正解常常是最長的那一個；
   - 字彙等級；
   - Firebase 禁用字元。
4. **兩次獨立盲解**：用不同模型、選項洗牌、看不到答案。兩次都和答案鍵一致、也都沒有回報「有兩個答案說得通」，才算通過；否則修改後重跑，或直接丟棄。
5. **使用者抽檢**：在 App 內的審題頁面（新做）抽 5%，每批至少 10 題。規則沿用 D-A11：抽到 1 題答案錯、或 2 題以上有問題，整批退回。
6. **發布**：寫入內容包和帳本 `content/ledger.csv`，記錄批次、作者模型、提示版本、盲解結果、抽檢結果和權利。
7. **上線後**：「這題有問題」的回報、AI 解析的質疑，以及 P4 的作答統計，都會回到待審清單。

產能目標是每週 300 題：2 個作者代理、2 個盲解代理，你每週抽檢約 15 題。

### 3.3 聽力音檔管線（P0 開始）

- **引擎**：**Kokoro-82M**（Apache-2.0）的網頁版 kokoro-js，在瀏覽器裡執行（D-2：電腦不安裝任何程式）。
  - 模型（q8，約 90 MB）下載到瀏覽器快取，可以隨時清除。
  - 產生器是開發工具：`tools/audio/generate.html` 加上只用 Python 標準函式庫的 `tools/audio/devserver.py`（只綁定 127.0.0.1），不隨網站發布。
  - MP3 在瀏覽器裡用 lamejs 編碼。
  - 腔調有美式和英式；澳洲腔見 D-6。
  - 不採用的方案：edge-tts（散布音檔的權利不明）；本機 Python 版 Kokoro、Piper（都需要安裝程式，違反 D-2）。
- **建置腳本**：`tools/audio/build.py` 讀取題目，依照 `M`/`W`/`M2`/`W2` 標記和每個題組指定的腔調分配聲音，產生分段音檔：
  - Part 2：問句和每個回應各一段，播放時依洗牌後的順序串接；(A)(B)(C) 的唸法也是共用的小音檔。
  - Part 3 和 4：對話或獨白一段，題目朗讀另外一段。
  
  輸出 MP3 單聲道（位元率在 spike 裡決定，約 32–48 kbps），加上 `audio/manifest.json`，記錄 ID、檔案、SHA-256、長度、聲音、引擎版本，以及每句話的起訖時間，供逐字稿同步用。
  - 只重建腳本、聲音或引擎有變動的題目。
- **自動檢查音檔**：同樣在瀏覽器裡，用 transformers.js 執行 Whisper（MIT 授權），把音檔轉回文字，和腳本比對。超過以下任一門檻，就修正讀音字典後重產：
  - 字詞錯誤率 > 5%；
  - 任何數字、時間、金額或專有名詞不一致。
- **播放規則**：
  - 練習模式：可以變速（0.8、1.0、1.2 倍）、重播、看逐字稿。
  - 模考模式：照正式考試，不能重播或變速，播完自動進下一題，作答間隔照正式節奏。
  - 第一次播放一定由使用者點擊開始（iOS 的限制）。
  - 找不到音檔或播放失敗時，改用裝置語音並標示出來。
- **說明語音**：自己撰寫，不使用 ETS 的官方說明文字（有著作權）。
- **容量**：全部約 8 小時，總量 120–170 MB。Service Worker 只快取用到的音檔，不預先全部下載。GitHub Pages 每月流量的軟上限約 100 GB；β 期間如果接近，就把音檔移到 Cloudflare R2 的免費額度（屆時另外決策）。

### 3.4 學習引擎（P2）

- **技能分類**：約 40 項。
  - Part 5：詞性、時態與語態、介系詞、連接詞、關係詞、代名詞、比較、搭配詞……
  - Part 6：上下文時態、連接副詞、插入句
  - Part 7：主旨、細節、推論、同義改寫、意圖、插入句位置、多篇整合
  - 聽力：照片描述、疑問詞問句、是非問句、間接回答、主旨、細節、推論、意圖、圖表

  舊題由 AI 標註，抽樣檢查後套用。
- **掌握度**：類 Elo 或 Rasch 的簡化模型。每項技能有能力值 θ，每道題有難度 b；答對機率是 σ(θ − b)，作答後更新。
  - b 的初始值來自編輯估計的 `lvl`；P4 用匿名作答統計校準。
  - 畫面上顯示掌握度和樣本數；樣本太少時標示「資料不足」。
- **選題**：每日計畫包含到期複習（FSRS）、弱項技能練習、新題接觸，衝刺期再加上限時題組。
  - 弱項練習把預估答對率控制在 60–75%，這是最適合學習的區間。
  - 每項安排都附上一句原因，例如「介系詞掌握度 52%，最近 7 天答錯 4 題」。
- **FSRS**：依公開的 FSRS 公式自行實作。如果參考 ts-fsrs（MIT 授權），會在檔頭註明出處。
  - 一開始用預設參數；累積 ≥1,000 次複習後，再用自己的資料最佳化參數。
  - 單字從 SM-2 變形轉換成 FSRS，舊的間隔資料保留。
- **診斷測驗**：約 30 題、15 分鐘，涵蓋所有 Part 和主要技能，用來設定 θ 的初始值。新使用者必做；舊使用者可以選做。
- **遷移練習**：答錯後，下一輪會出一道同技能、不同句子的題目。AI 變體題沿用 AI-10 的規則：只出現在錯題複習，不計入統計。
- **驗證**：用模擬學習者（已知能力值）跑 90 天，檢查三件事：掌握度能不能收斂、選題會不會長期忽略某項技能、每天的題量會不會失控。

### 3.5 評量與模考（P2–P3）

- **完整模考**：聽力約 45 分鐘，跟著音檔節奏進行；閱讀 75 分鐘。可以兩段連續考完，也可以分開考。
  - 有答案卡；可以中斷後接續，聽力從目前題組的開頭重來。
  - 錯題進入各回自己的錯題本。
- **報告**：
  - 依 Part 和技能的答對率；
  - 閱讀每題作答時間，以及 Part 7 有沒有寫完；
  - 和前幾次模考比較；
  - 對應的弱項練習連結。
- **分數區間**：預設不顯示（INV-04）。
  - P4 如果收到 ≥30 組「本 App 模考原始分＋近期正式成績」的自願回報，就建立對照模型，並公開誤差，例如「80% 的人落在 ±45 分內」。之後才顯示區間，並註明樣本數。
  - 收不到足夠資料時，維持只顯示原始分。

### 3.6 帳號、同步與資安（P1）

- **登入**：Firebase Auth 的 Google 登入（O-03）。可以先不登入、只用本機，之後再連結帳號。
- **資料結構**：`users/$uid/{profile, items/$id, srs/$id, mocks/$id, settings}`。
  - 每一筆都有 `u`（更新時間），同步時逐筆比較，較新的勝出，不再整份覆蓋。
  - 規則限制 `auth.uid === $uid`，並檢查每個欄位的型別、長度和數值範圍。
- **App Check**：用 reCAPTCHA，擋掉不是從我們網站送出的請求。
- **規則測試**：在 CI 裡用 Firebase 模擬器執行，涵蓋：讀寫別人的資料必須失敗、格式錯誤必須失敗、正常寫入必須成功。
- **舊同步代碼**：上線後 60 天內可以讀取並搬進帳號；之後改成唯讀，再過 30 天關閉（O-04）。
- **資料權利**：可以匯出全部資料（JSON），也可以刪除雲端資料、刪除帳號。本機資料可以一鍵清除。
- **既有保護維持不變**：CSP、SRI、no-referrer、自帶金鑰的隔離（INV-10–INV-12）。
- **文件**：
  - `docs/security/threat-model.md`；
  - 每次發布前的資安審查清單，延續 v1.3.1 的審查格式。

### 3.7 離線與效能（P1）

- **Service Worker**：
  - 預先快取 App 外殼（≤300 KB）；
  - 內容包和音檔在用到時才快取；
  - 快取有版本號；有新版時提示「重新整理」；
  - 準備一個緊急停用版本，可以讓所有使用者解除 Service Worker。
- **效能預算**由 CI 檢查，超過就不能部署：
  - 首次載入傳輸 ≤300 KB；
  - 單一內容包 ≤150 KB；
  - 主執行緒長任務 <200 ms。

### 3.8 工程與發布（P1）

- **模組化**：`app.js`（2,136 行）依職責拆成 ES 模組：狀態與遷移、排程、選題、各練習頁、模考、統計、設定。
  - 每個檔案 ≤600 行。
  - 拆之前先補測試，拆的過程不改行為。
  - 正式站仍然直接載入原始檔，不打包（D-A02）。
- **CI**（GitHub Actions），以下全部通過才能合併到 `master`：
  - `node --test`；
  - 內容 lint；
  - 規則測試；
  - Playwright 冒煙測試和主要流程（Chromium＋WebKit）；
  - axe 無障礙檢查；
  - 效能預算。
- **版本**：`tools/stamp.mjs` 自動產生版本號和快取參數，取代手動遞增 `?v=`。
- **錯誤紀錄**：攔截 `window.onerror` 和 `unhandledrejection`，存進本機的循環紀錄（最多 200 筆，不含作答內容）。設定頁可以匯出，使用者自己決定要不要寄給我們。這不算遙測（INV-08）。
- **Staging**：另開一個 GitHub Pages 站做預覽。流程是：CI 全部通過 → 部署到 staging → 你確認 → 推到 `master`。每一次推送都需要你明確核准（不變）。
- **回滾**：推回上一個版本的 commit，並搭配 Service Worker 的版本提示。這個流程寫在發布清單裡。

  - 內容權利：題目為原創；語音引擎的授權；照片的授權。
- **聯絡與支援**：聯絡信箱（O-05）、GitHub Issues 範本、常見問題。回報在 14 天內回覆。
