# TOEIC 900+ v1 改良版 — 驗證方法

> 狀態：草案，待使用者審閱
> 日期：2026-10-02
> 對應規格：[spec.md](spec.md)
> 本文件所有測試目前都是 `NOT RUN`。

## 1. 原則

1. **驗收單位是「一個 commit＋資料版本＋測試環境」。** 結果不會自動延用到下一個 commit。
2. **先寫預期，再執行。** 不能為了讓測試通過而改預期；規格要改就先改 spec.md。
3. **結果只有四種**：`PASS`（通過且有證據）、`FAIL`（失敗）、`BLOCKED`（缺外部條件，例如沒有實機）、`NOT RUN`（沒有執行）。沒有證據就不是 PASS。
4. **語法檢查不等於功能驗收。** `node --check` 只證明檔案能解析。
5. **作者不能替自己簽核。** 程式由 Claude 寫，所以每個版本的驗收由四件事共同構成：
   - 自動化測試全部通過（L1–L5）；
   - 一個沒參與實作的獨立審查代理，用 `code-review` skill 審查該版本的完整差異，並對照本規格；
   - 使用者完成實機檢查（L6）；
   - 使用者核准部署。
6. **題目由 AI 起草、使用者審核**，AI 不能核准自己寫的題目（L7）。

## 2. 驗證層級

| 層級 | 內容 | 工具 | 在哪裡跑 | 誰負責 | 開始於 |
|---|---|---|---|---|---|
| L1 靜態檢查 | 語法、版本一致性、內容 lint | `node --check`、`tools/check-version.mjs`、`tools/lint-content.mjs` | 本機＋CI | 自動 | v1.3（手動）／v1.4（CI） |
| L2 單元測試 | 學習規則、遷移、計分、同步判斷、語音邏輯 | `node:test`＋`vm` 載入器 | 本機＋CI | 自動 | v1.3（語音與代碼部分）／v1.4（全面） |
| L3 端對端測試 | 使用者流程、離線、XSS、CSP | Playwright（Chromium、WebKit iPhone 13） | 本機＋CI（Chromium） | 自動 | v1.4 |
| L4 Firebase 規則測試 | 讀寫權限與資料結構驗證 | Firebase Emulator Suite（需 Java 與 firebase-tools） | 本機 | Claude | v1.3 |
| L5 安全檢查 | XSS 字串矩陣、CSP 違規、原始碼中的機敏值 | L3 測試＋grep | 本機＋CI | 自動 | v1.4 |
| L6 實機檢查 | 聲音、安裝、離線、觸控、螢幕閱讀器 | 使用者的手機與電腦 | 實機 | 使用者 | 每個版本 |
| L7 內容審核 | 題目與單字的唯一正解、自然度、來源 | 審題工具（CNT-01） | 瀏覽器 | 使用者 | v1.6 |
| L8 上線後檢查 | 正式站版本、主控台錯誤、載入時間 | 唯讀的瀏覽器與 HTTP 檢查 | 正式站 | Claude | 每次部署後 |

**L4 的替代方案**：如果本機無法安裝 Java 或模擬器，改由使用者在 Firebase 主控台的「規則測試區」逐一執行本文件列出的案例，並截圖存證。這種情況要在證據包中註明。

**L2／L3 的語音替身**：測試注入假的 `speechSynthesis`，可以設定三種行為：
- `normal`：依序觸發 `start`、`end`；
- `silent`：從不觸發任何事件（模擬 iOS 阻擋或語音引擎故障）；
- `error`：立即觸發 `error`。

語音清單也可以設定（0 個英文、1 個英文、多種腔調）。

## 4. 不變條件的檢查方式

每個版本都要檢查，結果寫入證據包。

| ID | 檢查方式 |
|---|---|
| INV-01 | 單元測試：模擬開機流程，攔截 `save()`，確認在 `renderers.home()` 完成前呼叫次數為 0 |
| INV-02 | 內容 lint 與單元測試：所有會成為 key 的欄位不含 `. # $ / [ ]`；自訂題庫匯入的清洗測試 |
| INV-03 | 單元測試：`tests/fixtures/` 放 v1.0、v1.1 的合成存檔與備份檔（不使用真實使用者資料），每個版本都要能讀入，且欄位不遺失 |
| INV-04 | 端對端測試：所有畫面不出現「預估分數」或 10–990 範圍的分數 |
| INV-05 | ENG-08 的 XSS 測試；審查時檢查所有新增的 `innerHTML` 插值 |
| INV-06 | 內容 lint |
| INV-07 | 單元測試：匯入自訂題後，原有題目的索引不變 |
| INV-08 | 端對端測試：記錄全部網路請求，只允許本站、gstatic.com、Firebase 網域（v1.5 再加 Auth 必要網域） |
| INV-09 | 單元測試：錯題本與任何要寫入 Firebase 的物件，數值欄位都不是 `null` 或 `undefined` |

## 5. XSS 測試字串矩陣

所有使用者可控制的欄位都要測下列字串：

```text
<img src=x onerror=window.__xss=1>
"><svg onload=window.__xss=1>
" autofocus onfocus="window.__xss=1
'><script>window.__xss=1</script>
javascript:window.__xss=1
${7*7}
```

通過條件：測試結束時 `window.__xss` 仍是 `undefined`，畫面上看到原始字串，沒有 CSP 違規以外的錯誤。

## 6. 內容審核流程（L7）

**角色**：AI 作者（Claude）起草並自查；使用者是第二位審核者；使用者的判定是發布依據。

**步驟**：

1. Claude 起草題目，完成自查，在 `reviewRecords` 記錄 `self-check only`。
2. 使用者在審題工具中**先不看答案自己作答**，再看答案、證據、解析，給出判定：
   - **同意**：答案唯一、英文自然、解析正確、干擾項合理、看不出抄自官方或出版題目；
   - **有疑問**：必填原因；
   - **退回**：必填原因。
3. 使用者的答案和正解不同時，即使判定「同意」也自動標為「有疑問」。
4. 「有疑問」與「退回」的題目由 Claude 修改，版本號加 1，重新審核；不能只改狀態。沒有第三位審核者，所以兩人意見不一致時，**該題不上線**，而不是由 Claude 裁決。
5. Claude 對 10% 抽樣題目的特殊句子做網路搜尋比對，結果寫入來源欄位。

**每批審核報告**（存入證據包）：審核題數、同意率、使用者答案與正解不一致的題數、退回原因分類、修改後通過數、抽樣比對結果。

**對外宣稱前的額外條件**：如果要在 App 或對外說明中宣稱題目達到商業品質，先請一位英語教師抽樣複查（建議 10%，至少 30 題，優先高難度題），結果寫入證據包。

## 7. 證據包

每個版本建立 `.scratch/toeic-v1-improve/evidence/<版本>/`：

| 檔案 | 內容 |
|---|---|
| `run-manifest.md` | commit、分支、版本、題庫雜湊、測試環境（作業系統、瀏覽器、Node 版本、裝置型號）、日期、執行者 |
| `automated.txt` | 所有自動化測試的完整命令、輸出、結束碼 |
| `test-results.csv` | 測試 ID、需求 ID、層級、結果（PASS／FAIL／BLOCKED／NOT RUN）、證據位置、缺陷 ID |
| `manual-checklist.md` | L6 實機檢查的步驟、裝置、結果、截圖位置 |
| `review.md` | 獨立審查代理的審查結果與處理情形 |
| `content-review.md` | 該版本的審題報告（v1.6 起） |
| `defects.md` | 缺陷：嚴重度、重現步驟、預期與實際、根因、修正 commit、回歸測試 |
| `signoff.md` | 是否可發布、未解決的風險、使用者核准紀錄 |

證據包不得包含真實同步代碼、使用者姓名或真實作答紀錄。測試一律使用合成資料。

## 8. 發布閘門與回滾

**發布條件**（全部滿足才請使用者核准部署）：

1. 該版本所有測試案例都是 PASS；只有實機案例可以是 BLOCKED，而且必須列在 `signoff.md` 並經使用者接受。
2. P0、P1 缺陷為 0；P2 缺陷有說明與修正計畫，且經使用者接受。
3. 不變條件全部維持。
4. 獨立審查代理沒有未處理的高嚴重度發現。
5. 證據包完整。

**部署步驟**（使用者核准後）：

1. 合併到 `master`，推送。
2. 執行 L8 上線後檢查：正式站的 `APP_VERSION`、`?v=`、主控台錯誤、載入時間。
3. 若 Firebase 規則有變更，由使用者在主控台貼上（O-02），再執行 T-SEC-01-7。

**回滾**：

- 程式：在 `master` 上 `git revert` 該版本的合併 commit，遞增 `?v=`，推送。v1.4 起還要遞增 Service Worker 的快取名稱；若 Service Worker 本身有問題，部署緊急停用版本（ENG-05）。
- Firebase 規則：repo 中保留上一版規則檔，貼回主控台。
- 使用者資料：所有版本都必須能讀入舊格式（INV-03），所以程式回滾不需要轉換資料。

## 9. 缺陷分級

| 等級 | 定義 | 例子 | 處置 |
|---|---|---|---|
| P0 | 資料外洩、大量資料遺失、無法安全使用 | 讀到別人的資料、同步覆蓋全部進度 | 立即停止發布；已上線則回滾 |
| P1 | 核心學習流程錯誤、答案錯誤、計時錯誤、顯示誤導分數 | 正解錯誤、模擬考卡住、閱讀測驗時間可被暫停 | 不可發布 |
| P2 | 重要流程受影響但有替代做法 | 某機型需要按兩次播放 | 需使用者接受並排定修正 |
| P3 | 小問題 | 間距、文案標點 | 記錄並排入待辦 |

## 10. 商業級重新評分

每個版本上線後，依評估報告的九個面向重新評分：

- 只計算已上線且有證據的項目。
- 每個分數附上證據來源（測試 ID、證據包路徑或實機紀錄）。
- 更新評估報告 artifact，並在 `signoff.md` 記錄新舊分數。
- 和 spec.md §1 的目標對照，列出還沒達標的面向與原因。
