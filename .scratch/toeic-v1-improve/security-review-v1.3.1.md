# 資安審查：v1.3.1（AI 錯題解析）上線前

- 日期：2026-10-07
- 範圍：分支 `claude/toeic-v1-improve` 的 `b2313e8`，包含 v1.3.1 新增的 AI 功能，以及它所在的整個 App 與託管環境。v1.3.1 第一次把「會產生費用的機密」（API 金鑰）存進瀏覽器，所以舊有的弱點也重新評估了嚴重度。
- 審查者：Claude。v1.3.1 也是 Claude 寫的，所以這不是獨立審查。
- 結論：**目前不建議上線 v1.3.1。** 有 2 個高風險問題要先處理：H1 要改程式，H2 需要你決定。

## 威脅模型

要保護的東西：

| 資產 | 外洩的後果 |
|---|---|
| Anthropic API 金鑰（v1.3.1 新增） | 被盜用、產生費用 |
| 同步代碼 | 學習紀錄可以被讀取或覆蓋 |
| 學習紀錄 | 價值較低，但遺失或被竄改會影響使用 |

可能的攻擊來源：

1. 知道或猜到同步代碼的人。Firebase 規則允許任何人用代碼讀寫 `sync/<代碼>`。
2. 一個惡意的備份檔，被使用者匯入。
3. 和本 App 位於同一個網域（origin）的其他網頁。
4. 被入侵的第三方腳本（CDN）。
5. 使用者裝置上的瀏覽器擴充功能。

## 發現

### H1（高）：學習紀錄中的欄位未跳脫就寫進畫面，可以被注入腳本（儲存型 XSS）

- **已在本機瀏覽器實證。** 把以下欄位設成 `<img src=x onerror=…>` 後渲染畫面，有 6 處的腳本被執行：
  - `S.lastBackup`（題庫/備份頁，`app.js:1565`）
  - `S.targetScore`（「我的」頁，`views.js:37`）
  - `S.cat[*].r`（統計頁 `catBars`，`app.js:1098`）
  - `S.p6done[*]`、`S.p7done[*]`、`S.l34done[*]`（各練習列表的「最佳」成績）
- **攻擊路徑**：這些欄位都來自學習紀錄，而學習紀錄有三個入口完全沒有檢查型別：
  - 雲端同步拉取：`sync.js:62`，直接 `Object.assign`。
  - 匯入備份檔：`importBackupFile`，直接寫進 localStorage。
  - `load()`。
- **攻擊情境**：
  - 有人知道你的同步代碼，在雲端寫入一份惡意紀錄。你下次開 App 時，腳本就在你的頁面上執行，可以讀走 API 金鑰和同步代碼。
  - App 允許自訂同步代碼（4 個字以上）。如果用了好猜的代碼（例如 `toeic`），風險就更高。系統產生的代碼約有 50 位元的隨機性，猜不到。
- **既有問題**：線上的 v1.3.0（以及更早的版本）也有這個問題，不是 v1.3.1 新產生的。不過 v1.3.1 讓瀏覽器裡多了一把會產生費用的金鑰，影響因此升高。
- 自訂題庫（`bank`）的文字欄位已經有跳脫，但同步與備份的入口也沒有重新驗證格式。格式錯誤的題目會讓頁面出錯，屬於可用性問題。
- **修正**：
  1. 新增 `sanitizeState()`，在 `load()`、同步拉取、備份匯入三個入口逐欄檢查型別。日期必須符合 `YYYY-MM-DD`，次數必須是非負整數，模考模式必須在允許清單內。不合格的值丟棄或歸零。
  2. 同步與備份匯入的自訂題庫，逐題用 `validateItem` 篩選。
  3. 上述 6 處輸出也包上 `esc()`，做雙重防護。
  4. 補上回歸測試：把 XSS 字串放進每一個欄位，確認不會執行。

### H2（高，架構）：本 App 和你的另外 3 個網站共用同一個網域

- **已確認**：`realsnova.github.io` 底下有 4 個 GitHub Pages 網站，它們是同一個 origin，共用同一份 localStorage：
  - `toeic-900`（本 App）
  - `A1_mover_Vocabulary_Gemini`
  - `AI_Mover_A1_Claude`
  - `A1-Movers-Game-Gemini`
- **後果**：任何一個網站上執行的程式，都可以直接讀取 `toeic900_ai`（API 金鑰）和 `toeic900_sync`（同步代碼）。
- 其中 2 個網站從 `cdn.jsdelivr.net` 載入第三方腳本，而且**沒有做完整性檢查（SRI）**：
  - `canvas-confetti@1.6.0`
  - `@twemoji/api@15.1.0`

  只要這些套件或 CDN 被入侵，或者那些網站本身有 XSS，就可以讀走本 App 的金鑰。
- 這是 GitHub Pages「專案網站」的結構限制，靠本 App 的程式碼無法完全解決。
- **修正選項**（需要你決定）：
  - **A. 把本 App 搬到獨立網域**（最徹底）。免費的做法：
    - 建一個 GitHub 組織（例如 `toeic900`），網址變成 `toeic900.github.io`；
    - 或改用 Cloudflare Pages（`xxx.pages.dev`）。

    搬家後，舊網址的本機紀錄不會自動跟過去，要先用同步代碼或備份檔帶過去。
  - **B. 金鑰不長期保存**：預設只存在這次開啟的分頁（`sessionStorage`），關掉 App 就要重新貼上；另外提供「在這台裝置記住」的選項，勾選時清楚說明風險。可以降低其他網站讀到金鑰的機會，但不能完全排除。
  - **C. 接受風險**：只靠用量上限控制損失。
  - **不論選哪一個**：都建議在 Anthropic 主控台為這個用途建立專用的 workspace 與金鑰，並設定每月用量上限，把最壞情況的損失限制在上限內。

### M1（中）：沒有內容安全政策（CSP）

- 原本排在 v1.4（ENG-06）。App 本身沒有行內腳本或 `on*=` 屬性，所以可以直接加上不含 `'unsafe-inline'` 的 `script-src`。
- 這樣一來，即使將來又出現像 H1 那樣的漏洞，注入的 `onerror=` 也不會被執行。
- `connect-src` 可以限制成只連 Firebase 和 api.anthropic.com，多數外送資料的方式也會被擋下。
- **修正**：把 ENG-06 提前到 v1.3.1。Firebase Realtime Database 在 WebSocket 無法使用時，會改用長輪詢載入腳本，所以 `script-src` 要加上 `https://*.firebasedatabase.app`。

### M2（中）：Firebase SDK 沒有完整性檢查

- 已確認 `www.gstatic.com/firebasejs/10.13.2/*` 有提供 CORS 標頭，而且版本固定（快取一年），所以可以加上 `integrity` 與 `crossorigin="anonymous"`。已算出兩個檔案的 sha384 雜湊值。
- **修正**：在 `index.html` 加上 SRI。

### M3（中）：自訂同步代碼可以太短、太好猜

- 規則允許 4 到 64 個字。H1 修好之後，猜到代碼也只能讀取或覆蓋學習紀錄，不能再執行腳本，但仍然是隱私問題。
- **修正**：少於 10 個英數字的代碼（系統產生的代碼正好 10 個）在套用前要確認，並建議改用系統產生的代碼。已經在用的短代碼保持可用，否則其他裝置會無法套用；但設定頁會提醒更換。

### L1（低）：可以被別的網站嵌入（點擊劫持）

- GitHub Pages 不能設定 `X-Frame-Options`，而且 CSP 的 `frame-ancestors` 不能寫在 meta 標籤裡。
- 最壞情況只是被誘導按下 AI 解析，花費幾美分。
- **修正**：開機時如果發現自己被嵌入框架，就不顯示 AI 設定與 AI 按鈕。

### L2（低，自帶金鑰的本質）：瀏覽器擴充功能看得到金鑰

設定頁已有說明。可以處理的方式只有用量上限，以及不用時刪除金鑰。

### L3（低）：AI 提示注入

- 自訂題庫的內容會被送給 AI。惡意題目可能讓 AI 輸出誤導的文字。
- 不過輸出一律以純文字顯示，也不會影響計分（INV-12），而且 API 請求本身不帶任何其他資料，所以無法透過 AI 取得金鑰。
- 維持現狀。

## 確認沒有問題的項目

- **API 金鑰不外流到 App 自己的資料流**：金鑰不在學習紀錄、不在雲端同步內容、不在備份檔、不在疑似問題清單或匯出檔，也不出現在錯誤訊息裡（有遮蔽處理）；全程沒有輸出到主控台。有單元測試涵蓋。
- **AI 回應**：一律經過 `esc()` 以純文字顯示，已實證 `<img onerror>` 不會執行。
- **網路請求**：只連到 `api.anthropic.com`。沒有金鑰時，不會發出任何 AI 請求。
- **Firebase 存取**：未登入讀取根目錄與 `/sync` 清單都回傳 401，無法列出所有人的同步代碼（2026-10-07 實測）。
- **Firebase `apiKey`**：這是網頁用的公開設定，本來就設計成公開，不是機密。
- **Git 歷史**：沒有真實的 API 金鑰、GitHub token 或私鑰。測試只用明顯的假金鑰。
- **傳輸加密**：正式站有 HSTS。

## 建議的處理順序

1. 修 H1、M1、M2、M3、L1，以及自訂題庫的驗證。這些都是程式修正，不需要你做決定，可以一起在 v1.3.1 完成。H1 也會修好線上 v1.3.0 的既有漏洞。
2. 你決定 H2 的處理方式（A、B 或 C）。
3. 修正後重跑全部測試，再做一次 XSS 實證，並請獨立審查代理看修正的部分。
4. 你核准後上線。

| 編號 | 狀態 | 驗證 |
|---|---|---|
| H1 | 已修正 | `sanitizeState()` 用在三個入口；自訂題庫逐題驗證；6 處輸出加上 `esc()`。單元測試 sec-H1-1～6（惡意紀錄、舊版資料保留、同步拉取、題庫驗證、輸出跳脫、開機順序）。瀏覽器實測：放入 XSS 字串後渲染 11 個頁面，沒有任何 `img[src=x]`，欄位都已歸零或移除 |

全部測試 72 個通過。

**仍需注意**：
- 勾選「記住」後，H2 的風險仍然存在。
- CSP 寫在 meta 標籤，無法防止被別的網站嵌入（`frame-ancestors` 不能用 meta 設定），只能靠 L1 的處理。
- 如果之後升級 Firebase SDK 版本，要重新計算 SRI 雜湊值，否則 SDK 會載入失敗，同步也會停止運作。
